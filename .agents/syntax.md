# Pattern syntax

`addRoute` pipeline: `absolutePattern` (see [below](#leading-)) → `checkConstraints` → `starGroups` (a `(.*)` group is a `*`, a `:name(.*)` one keyed by name, see [matching.md](matching.md#greedy-)) → `expandGroupDelimiters` → `encodeEscapes` / `splitRoute` → `expandModifiers` (`:x+` → `**:x`, `:x*` → `**:x` + the route without it, see [matching.md](matching.md#empty-segments-and-normalization); `pre-:x?` → `pre-:x` + `pre-`, but after a capture it stays for `getParamRegexp`, see [below](#params-sharing-a-segment)) → `splitStar` (a `*` inside a segment: its segment-local pieces around a `**`, see [matching.md](matching.md#greedy-)) → per segment `segmentKey` (static key) or `getParamRegexp` / `addName`, both percent-encoding literal text (`encodeLiteral`, see [below](#percent-encoding)). Each helper bails early when its trigger is absent (`\`, `�`, a tab / LF / CR, `(.*)`, `{`, trailing `?`/`+`/`*`, `(`/`{`/`}`, an encode-set char), so plain routes skip the scanners. Keep those guards.

## Leading `/`

A relative pattern gets a `/` (`foo/:id` is `/foo/:id`; URLPattern never matches one on an absolute path). `absolutePattern()` (`operations/_utils.ts`) is the one rule, used by `addRoute`, `removeRoute` and `routeToRegExp`: a pattern starting with `/` or `{` is left alone. A leading `{…}` group can't be prefixed as a whole: `{/:a}?/b` is absolute in URLPattern (WPT gives `{/:foo}bar` as the canonical form of `/:foo\bar`), and a `/` in front would add an empty first segment (`//b`). So `expandGroupDelimiters` applies `absolutePattern` to each expansion of a leading group (`pre === ""`): one starting with `/` is absolute (`/:a/b`), the empty one is the root (`{/:a}?` is `/:a` or `/`, like `/:a?`), any other is relative and gets a `/` (`{a}?/b` is `/a/b` or `/b`, `{a}?b` is `/ab` or `/b`; URLPattern matches only `/b` and nothing for the relative forms), and one starting with `{` is the next group's (`{/a}?{/:b}?/c`). Escaped braces (`\{/a\}`) are literals: relative. Insert-time only: lookup is untouched.

- **Reserved:** text right after a leading `{/…}?` throws (`{/a}?b`, `{/:a}?.png`, `{/a}?{.json}?`, `{/a}?{b}?/c`): the pattern is absolute, but without the group the route would be relative, a form URLPattern gives no meaning (`{/a}?b` matches only `/ab` there; the same rule would have made it match `/b`, `{/:a}?.png` `/.png`, `{/a}?{.json}?` `/.json`). After it come `/`, another `{/…}` group, or nothing. `{/…}+` / `{/…}*` throw as anywhere.
- **Malformed `{…`** (no group to expand): `addRoute` rejects it in `checkConstraints`; `removeRoute` doesn't validate, so `_removeRoute` returns when an unexpanded path has no leading `/` (it would split into another route's segments: `{oops/users/:id` is `/users/:id`). It threads `input` like `_add`, so the reserved syntax its expansions check (`{…}+`, text after a leading `{/…}?`, a misplaced modifier) throws quoting the pattern as written, never an expansion.
- **Removal identity:** `expandedRouteId` reads a leading-group pattern after a `/` (the split drops a path's first piece) and marks it with a `{`, which no other identity starts with: read after a `/`, `{a}?/b` would be the text of `/{a}?/b`, and both register `/a/b`. The `/` alone keeps `{/:a}?/b` apart from a plain `/b`, `/{/:a}?/b` or `{x/:a}?/b`.
- **Unnamed captures:** `skipGroup` counts a relative leading group's captures after its `/` (`{(\d+)}?/*` on `/x` is `{ 1: "x" }`).
- `routeToRegExp`: `inlineOptionalGroup` builds the full expansion with the same `/` (`{a}?/b` is `(?:\/a)?\/b`); a leading group with nothing after it (`{/:a}?`) has an empty base and falls back to alternation.
- `regExpToRoute`: a root optional of whole segments with no segment to merge onto comes back as a leading group (`^(?:\/(?<_0>\d+))?\/b` → `{/(\d+)}?/b`; `mergeGroup`). Only at the top level and only when the body has no `\/` before it (`/{/a}?` is an empty first segment, then the group). The result's groups are expanded like `addRoute` does, so text after it throws (`^(?:\/a)?(?:b)?\/c`); a body holding a group throws in `mergeGroup` (`^(?:\/a(?:\/b)?)?\/c` would be `{/a{/b}?}?/c`, after a segment too).
- Types (`InferRouteParams`) need nothing: they read names, not segments. A greedy `*` in a leading group is a catch-all as anywhere (`{/*}?/b` is `/*/b` or `/b`).

## Escapes

Any `\x` outside a constraint is a literal `x`, as in URLPattern (`/foo\.bar` matches `/foo.bar`, `\\` is a `\`). Inside a constraint it is regex (`(\d+)`). One escape model, in `operations/_utils.ts`, used by the router and `routeToRegExp` alike (#227):

- `encodeEscapes()` hides `\:` `\(` `\)` `\{` `\}` `\\` behind U+FFFD + their index in `ESCAPABLE` before splitting, so no scan reads them as syntax; `\\` is one of them so pairs read left to right (`\\:x` is `\` + `:x`). This also applies inside constraints (`\)` doesn't close one).
- Static keys (`segmentKey`): other `\x` → `x`, then `decodeEscapes(s, "")`.
- Dynamic segments (`getParamRegexp`): other `\x` outside a group → U+FFFE + `x` (`\*` stays an escape so it is no wildcard), or its percent-encoding when `x` is in the encode set; placeholders decode to U+FFFE + char after params and groups are named (an escaped `{` / `}` at depth 0 is encoded right away); U+FFFE pairs then become regex-safe literals. Unescaped regex chars outside a group (`. $ | [ ] )`) are literals too, as in a static segment (`/api/*$`, a stray `)`); `^` (`/x/^:id`) is percent-encoded. A `:` inside a group becomes U+FFFE + `:`, so a `(?:…)` inside a constraint or unnamed group is never read as a param (the name replace skips it with a look-behind).
- `routeToRegExp` classifies segments with `segmentKey(encodeEscapes(s))`, reads modifiers from the encoded text too (`\:x?` has none), emits static keys regex-escaped and dynamic segments through `getParamRegexp` (with `_N` unnamed keys), so escapes can't drift between the two.

## Percent-encoding

Literal pattern text is percent-encoded like URLPattern canonicalizes a pathname pattern, so a route matches the encoded pathname `new URL()` gives; lookup input is never decoded or encoded (hot path untouched). `encodeLiteral()` (`operations/_utils.ts`) is the one encoder, verified against Node 24's `URLPattern` and `new URL()` (WPT `PERCENT_ENCODING_CASES`):

- The URL path percent-encode set: C0 controls, space, `"#<>?^\`{}`, U+007F and up, as UTF-8 upper-case `%XX` (`encodeURIComponent` on each run). `%` is never touched, so `%XX` stays as written (`%c3%a9` is not `%C3%A9`, a lone `%` or `%zz` is literal). Other ASCII (`|[]'!$&=@;,~+`) is kept.
- A lone surrogate becomes U+FFFD (`%EF%BF%BD`), as in URLPattern and `new URL()`; no `URIError` can leak. U+FFFD-U+FFFF are left alone: internal placeholders (U+FFFF reserved), rejected in a route by `checkConstraints`.
- A raw tab / LF / CR throws (`checkConstraints`, see [below](#reserved-syntax)): URLPattern strips it from a pattern (URL parsing: `/a\tb` is `/ab` there), while encoding it would match `%09`, so the same pattern would match different paths. Write `%09` / `%0A` / `%0D`.
- Runtime difference: `^` is in the URL path percent-encode set and is encoded (Node 24 and Bun encode it in `new URL()` and `URLPattern`), but Deno 2.9 leaves it raw in both (`new URL("http://h/a^b").pathname` is `/a^b`), so a route with a literal `^` misses Deno's pathname unless the caller encodes it. Kept: it follows the spec, and lookup input is never touched (README "Percent-encoding").
- Literal text only, after syntax is read: `segmentKey` encodes the static key after `\x` → `x` and `decodeEscapes`; `getParamRegexp` encodes depth-0 literals in its scan loop (a gate regex skips plain chars; a surrogate pair is read at once; an encoded `%XX` is emitted raw, it is no syntax; an escaped `{` / `}` placeholder, index 3 / 4 of `ESCAPABLE`, is encoded there; the `?` of an in-place optional param, `*-:x?`, is syntax and stays raw for the name replace, pinned by `PERCENT_ENCODING_CASES`). So `/:café` still throws `invalid param name`, `\é` / `\{` / `\?` are literals that get encoded, and a constraint is regex, never encoded (`:x(é)` matches a raw `é` only; URLPattern rejects non-ASCII there).
- Everything derived reads the tree's keys and regexes, so `removeRoute` (via `segmentKey` / `expandedRouteId`, compared through `routeId`), `routeToRegExp`, `routeNodeKeys`, overlap and the compiler (static map keys, codegen literals) agree: `/café` and `/caf%C3%A9` are one route, and so are `/café-:id` and `/caf%C3%A9-:id` (`routeId` / `dynamicKey` compare a dynamic segment's identity encoded the same way, constraints kept as written). `encodeLiteral` bails with one `test` on plain text (a no-match `replace` cost more at insert).
- `regExpToRoute` keeps `%XX` as written (decoding could change the route: `%2F`, `%25`) and throws on a literal char outside a constraint that `encodeLiteral` would change (`é`, space, `\{`, `\?`, `\^`) or a U+FFFD-U+FFFF placeholder: no route matches it (the error names the encoded form to write). A raw tab / LF / CR inside a constraint throws too (`addRoute` rejects it; a `\t` escape is kept as written).

## Group delimiters `{…}`

`_group-delimiters.ts` expands `{…}` and `{…}?` before insert/remove/regexp (a lone optional param group inside a segment, `*-{:x}?`, is rewritten to `*-:x?` instead, see [above](#params-sharing-a-segment)). `scanFirstGroup()` is shared with `inlineOptionalGroup()` (`regexp.ts`) so both classify groups identically; it returns a `[pre, body, suf, mod]` tuple (smaller core bundle than an object). A `{` / `}` ends a param name, as in URLPattern: `scanFirstGroup` escapes a name char (`[\w$]` or non-ASCII, `NAME_CHAR`) that starts `body` or `suf`, which would otherwise join onto a `:name` once expanded (`/:a{b}?` → `/:a\b` + `/:a`, `/:foo{}bar` → `/:foo\bar`). Both start outside any constraint, where a `\x` is always a literal `x`, so the escape is a no-op after anything but a name and needs no check (bundle size).

A `(` there would still read as the name's constraint, and a `?` / `+` / `*` as its modifier, so expansions are joined by `joinGroup(a, b)` (`expandGroupDelimiters` and `inlineOptionalGroup`, which must build the same strings): where `a` ends in a bare `:name` (its `:` not escaped) and `b` starts with a `(`, the param gets the lazy constraint it has anyway in a shared segment, spelled without a `/` (`splitRoute` would cut `[^/]`): `/{:foo}(\d+)` → `/:foo([^\x2f]+?)(\d+)`, and the group is an unnamed capture numbered like any other, as in URLPattern (`/a12` → `foo: "a"`, `0: "12"`). `getParamRegexp` emits that constraint as `[^/]+?` where a `(` (or the U+FFFF below) follows it, so tree, compiler and `routeToRegExp` (`LAZY_NAME`, `mergeCapture`) see the plain lazy name; elsewhere (a hand-written `/:x([^\x2f]+?)`) it stays as written, so `regExpToRoute` gives the route back with its constraint and rank. A `(.*)` there is a `*` and gets no constraint: `starGroups` writes it after U+FFFF (`/{:foo}(.*)` → `/:foo\uFFFF*`, `:foo` lazy as above, then the greedy `*`), which `joinGroup` keeps only after a `:name`, group or `*`. This covers every junction: `pre|body`, `body|suf` and `pre|suf` (`/:foo{x}?(\d+)` without the `x`, `/:foo{}(\d+)`), and sequential groups (`/{:foo}{(\d+)}` expands twice). Where `b` starts with `?` / `+` / `*` after a `:name`, `)` or `*` it throws (see below). No constraint is added after a `**:name`: it ends its segment, so `/**:x{}(y)` throws `invalid param name "x(y)"`, as before. It runs once per group expansion, never on a plain route. Why a join and not the tuple: a `:name` ending `pre` is followed by `body` in one expansion and by `suf` in the other, and only the one with a `(` needs the constraint (on a whole-segment `:name` it would add a regex param's weight). Why a constraint and not a marker char: every derived API (overlap, `routeNodeKeys`, `regExpToRoute`) already reads it.

## Reserved syntax

Syntax with no defined meaning throws `rou3: <what> (<route as written>)` (`invalidSyntax()`), so it can get a meaning later without a breaking change. Checks sit where the pipeline already looks:

- `checkConstraints` (route level): a raw tab, LF or CR anywhere, escaped (`\<tab>`) and inside a constraint too (`/:x(a<tab>b)`): URLPattern drops it outside a regexp group, so `/a<tab>b` would silently match `%09` here and `/ab` there; inside a group URLPattern keeps it, but no pathname (`new URL()` strips them, `%09` otherwise) has one raw, so it could never match: rejecting it everywhere is one check (write `%09` / `%0A` / `%0D`; the regex escapes `\t` / `\n` / `\r` in a constraint stay valid, and dead, as in URLPattern). A U+FFFD-U+FFFF char, the internal placeholders (`encodeEscapes`' `\uFFFD`, `getParamRegexp`'s `\uFFFE`, `starGroups`' `\uFFFF` before a `*`), which a route could otherwise write as syntax (`/a/\uFFFD0x` would read as an escaped `:`). Both share one regex and message (bundle size), checked in the same early bail; a `(` that does not close in its own segment, including a `/` inside a constraint (one message for both causes, bundle size); a `^` / `$` outside a class, a look-around or a numbered backreference (`\1`) in a constraint (the tree tests the segment alone, so they see its ends and count its groups; the inline regex sees the rest of the path and all its groups); a capturing group inside a constraint, unnamed or `(?<name>…)` (`/:x((a))`, `/a/((b)c)`, `/:n/:x((?<n>a))`: a stray param that could collide with a route param or unnamed key; groups are removed innermost-out and a capturing one leaves a `\0`, like a backreference, that its enclosing group trips on, also inside a class: `:x([()])` compiled to `[(?<_0>)]`, and `starGroups` would read `:x([(.*)])` as `[*]`; URLPattern rejects both). Only `(?:…)` may sit inside a constraint. A `--` / `&&` in a class (`/([[a-z]--a])`, `/:x([\w&&b])`): a set operation under URLPattern's `v` flag, plain chars in rou3's RegExp (compiled without `v`, which would reject constraints valid today: `\m`, a raw `(` / `-` in a class). `classSetOp()` (shared with `regExpToRoute`) reads classes innermost-out as `v` nests them, escapes dropped (`[a\-\-b]` is the literal spelling), so one outside a class (`(a--b)`, `([a]--[b])`) or in path text stays valid; it bails without a `--` / `&&`. The compiler's `_normalizeGroups` fallback (a non-identifier group name) is unreachable through `addRoute` (every group name is an identifier) and kept as a defensive path, pinned in `compiler.test.ts` with a hand-patched entry. Escapes are replaced by `_` (a backreference by `\0`) first, so `\(?=` is no look-ahead; after dropping escapes and constraints, a `\` that escapes nothing (`\/`, a trailing `\`) and unbalanced or nested `{}`. A stray `)` is literal.
- `expandGroupDelimiters`: `{…}+`, `{…}*`; text right after a leading `{/…}?` (`{/a}?b`, see [above](#leading-)); via `joinGroup`, a `?` / `+` / `*` that a group's `{` / `}` puts right after a `:name`, a group of its segment or a `*` (a stray `)` is a literal: `/a){*}` is valid; the group is read as `(` … a `)` with no `\` right before it, so `(a\\){?}` slips through to the modifier reading) (`/{:x}{*}`, `/{:x}?*`, `/:x{}?*`, `/{:x}{?}`, `/:x(\d+){?}`, `/*{*}`): it would be a modifier on the param or group (`/{:x}{*}` was `/:x*`, `/*{*}` a `**`), URLPattern reads `:x` then `*`, two `*`s, or rejects `{?}`. A modifier on the unnamed group after one throws in `expandModifiers` / `getParamRegexp` like any other (`/{:x}(y)?` was an optional `:x(y)`).
- `expandModifiers`: `+` / `*` on anything but a whole-segment `:name` (`:x(\d+)?` and `pre-:x?` are fine), and a `?` on a `**:name` (the `**` is no text before the param).
- A modifier on a `(.*)` / `:name(.*)` (a catch-all, like `*?`): `starGroups` leaves a `(.*)*` / `:name(.*)*` (rejected as a group or constrained param with a `*`) and writes the others as `*?` / `*+`, which `getParamRegexp` rejects. `MISPLACED_MODIFIER` names catch-alls.
- `getParamRegexp` (depth 0): an invalid name after `:` (it reads the `\w`, `$` and non-ASCII run, so `:`, `:0`, `:1st`, `:café` and `:id$` all throw `invalid param name` naming the run); a group that is empty or starts with `?`; a raw `?` / `+` quantifier (a `?` ending the segment right after a `:name` / `:name(…)`, `PARAM_MODIFIER`, is the in-place optional); a `*` right after a name, group or `*` (ambiguous with a modifier; `a**b`, `x**`: a mid-segment `**`, which `splitStar` already reports with this message, while a segment starting with `**` is read as `*` by `splitRoute`, `/**.md` = `/*.md`). Two `*`s apart in a segment (`file-*-*`) are two catch-alls (`oneCatchAll`).
- `_add`, static segment: an unescaped `?` (`/foo?`, `/a/b?/c`, `\:x?`): lookup paths never hold a query string, so it could never match. `\?` is a literal; `+` / `*` stay literal in a static segment (`/c++`). Shares `MISPLACED_MODIFIER` (where each goes: `?` after `:name` / `:name(…)`, `+` / `*` after a whole-segment `:name`, none after `**:name`; and the escape) with the modifier errors and the mid-segment `**` (one message, bundle size).
- `addName()`: a name that is not `[A-Za-z_]\w*` (quoted as written: a `**:name` runs to its segment's end, so the quote drops the `\` `scanFirstGroup` puts before a name char outside a constraint, `/a/**:x{s}?` names `"xs"`, and decodes `encodeEscapes`' placeholders, `/a/**:x\:y` names `"x\:y"`; a hand-written `\` + name char there is dropped too, the two can't be told apart); a name repeated within one expansion (a bare `**` counts as `_`, its deprecated alias): `rou3: duplicate param name "x" (…)`. `getParamRegexp` records its names here while scanning, before any regex is built.

`routeToRegExp` validates by calling `addRoute` on a throwaway router, so every error is the router's. Deliberately accepted: stray `)`, `+` / `*` in static segments (`/c++`), `\b` / `\B` in a constraint (a segment end and a `/` are both non-word). Known gap: a lone `(` / `)` inside a class in a constraint (`:x([(])`, `:x([)])`) is mis-parsed (a pair throws, above); escape it (`:x([\(])`).

Pinned by `RESERVED_SYNTAX_ROUTES` (`test/_regexp-cases.ts`, against `addRoute`, `routeToRegExp`, `routeNodeKeys`, `routesOverlap`), the accepted list in `regexp.test.ts` (and its class set-operation messages), WPT `RESERVED_PATTERNS`, `TAB_NEWLINE_PATTERNS` (`wpt.test.ts`: every strategy throws, URLPattern drops them), and `star.test.ts` (`(.*)` modifiers).

## Params sharing a segment

URLPattern semantics, so the same pattern splits a segment the same way everywhere:

- **Lazy `:name`:** `getParamRegexp` emits `[^/]+?` for an unconstrained `:name` (it only sees segments that aren't a lone `:name`), so the first of several params takes as little as possible: `:a-:b` on `x-y-z` is `x` + `y-z`, `:name.:ext` on `a.tar.gz` is `a` + `tar.gz`, `:a:b` on `xyz` is `x` + `yz`. With one param the literals around it fix its value, so lazy vs greedy only shows with several. A `*` is a greedy catch-all (URLPattern's `(.*)`, see [matching.md](matching.md#greedy-)): in its segment the piece is a greedy `([^/]*)`, an unnamed group numbered left to right with the others (`(\d+)-*` keys the group `0`, the `*` `1`), so `*-:a` on `x-y-z` is `x-y` + `z`, and on `x/y-z` `x/y` + `z`. A constraint keeps the user's quantifiers. The compiler reuses the tree's RegExps and `routeToRegExp` the same `getParamRegexp` source.
- **`pre-:x?`** (a `?` on a param that does not start its segment, `pre-:x(\d+)?` too) makes only the param optional, as in URLPattern. A whole-segment `:x?` keeps its meaning (an optional segment); `/{pre-:x}?` is the way to drop the whole segment. `+` / `*` there throw. Two forms, the same match set and split as URLPattern's one regex `pre-(?:(?<x>…))?`:
  - After plain text (`segmentKey` of the text before the param is a static key), `expandModifiers` expands it to `pre-:x` and `pre-`, as `pre-{:x}?` would: `pre-` stays a static node (static > param priority), and nothing before the param can take its text.
  - After a capture (`*-:x?`, `:a(\d+):b?`, `:a-:b?`, `:a:b?`, `*:x?`), `expandModifiers` leaves it and `getParamRegexp` compiles it in place, `(?:(?<x>…))?` at the end of the segment's regex. One regex tries the greedy capture's longest value first, so it takes what it can (`/*-:x?` on `/--` is `{0:"-"}`, `/:a(\d+):b?` on `/12` `{a:"12"}`); two routes would let the one with the param win. It is one entry: `findAllRoutes` lists the route once, and it weighs as a passing regex plus a required last param, also after a lone `:name` (`/e/:a:b?` ties `/e/:id(\d+)` on `/e/1`, registration order decides, and beats a plain `:id` sibling on every path, on deeper nodes too: `/e/:a:b?/x` over `/e/:id/x`, though both match the same paths; README "Result ordering") or a lone `*` (`/a/*:x?`'s segment is required, like `/a/*.png`'s: no match on `/a`). From the end (`rankFromEnd`, the compiler's `rankDescriptor`), a segment of captures alone with at most one required `:name` (`*:a`, `:a:b?`, `*:x?`, `*:a:b?`) ranks as a plain param, 0 (`paramsMap`'s `plain` flag, set by `_add`): it matches any non-empty value (or any value), so it restricts nothing more, and as a regex param `/**/:a:b?` would beat the narrower `/b/:id` and `/b/**`. Two required names (`:a:b`) need two chars: a regex param, 2. An absent param is an unset group, so it has no key: `getMatchParams` skips `undefined` groups, the compiler spreads it in only when set ([compiler.md](compiler.md#codegen-invariants)). `routeToRegExp` emits the same `getParamRegexp` source for both forms.
  - A group holding only an optional param, after text and ending its segment (`*-{:x}?`, `:a(\d+){:b}?`, `pre-{:x}?`), is that `:x?`, as URLPattern reads it: `expandGroupDelimiters` rewrites it before expanding (`inlineOptionalGroup` sees the single route and defers). At the start of a segment (`/{:x}?`) it stays a group, as in URLPattern. So does one with more of its segment after it (`/*-{:x}?(y)`: an in-place `?` must end the segment), which `joinGroup` joins (the `(y)` is an unnamed capture next to `:x`); its two routes match like URLPattern's regex unless a greedy capture before the group could take its text (`/*-{:x}?(y)` on `/a--y` is `{0:"a", x:"-", 1:"y"}`, URLPattern `{0:"a-", 1:"y"}`), pinned in `find.test.ts`. Groups with literals don't follow: `/media/*{.webp}?` and `*-{x-:y}?` still expand, and the route with the group wins (README "Differences from URLPattern"). Nor does a catch-all before an optional segment (`/:a+/:b?` on `/x/y` is `{a:"x", b:"y"}`, URLPattern `{a:"x/y"}`): segments after `**` match from the end, ranked by `rankFromEnd`.

## Param names and capture-group names

Name grammar everywhere: `[A-Za-z_]\w*`, as in URLPattern restricted to ASCII: a `-` ends a name (`:test-id` is `:test` + `-id`, `:year-:month` two params), a digit can't start one (`:0` would collide with the unnamed key `"0"`), and a non-ASCII char or `$` right after one throws (part of the name in URLPattern, a JS identifier: `:id$` is `id$` there; `:caf\é` and `:id\$` are literals). Sites to keep in sync: `addName`, `getParamRegexp` and `_add` (`add.ts`), `expandModifiers`, `NAME_CHAR` (`_group-delimiters.ts`), every `regexp.ts` site, `paramName()` / the name-extending-literal escape in `reverseSegment` (`regexp-to-route.ts`), `ExtractParams` / `NameRun` / `ValidName` (`types.ts`; `ExtractParams` skips the `:` of `(?:` and also keys every `**:name`, `ExtractWildcards` numbers the `*`s, bare `**`s and unnamed `(…)` groups over the whole pattern (tail-recursive, escape aware, plain text skipped 8 chars at a time so 1000-char routes stay in TS's recursion limit; `StripParams` replaces a param's name, constraint and modifier with a `:`, keeping an escaped `\:`, a `(?:` and a `*` in its segment, so a `*` before a param isn't read as ending the route) as `[key, may be unset, bare **]`: a `**`, a whole-segment `*` that ends the route (also before a last `{…}?`: `S`, the previous char is a `/`) and any capture in an optional `{…}?` group may be unset, a `*` is set otherwise (`""` at least), `**<text>` is one `*`-like key (also `**{.md}?`'s `*.md` route), and a bare `**` adds the deprecated `_?` alias). Types read the name run like `getParamRegexp` (`[\w$]`, ASCII only) but don't validate routes: a run `addRoute` rejects (`:0`, `:id$`) gives no key.

Named capture groups need identifiers, so every regex-emitting path goes through `_group-names.ts`:

- `toGroupName()`: valid identifiers pass unchanged; names in the `__rou3_` space and `_N`-shaped ones (the only route names that need it) become `__rou3_esc_` + (`_` → `__`, `-` → `_h`). The `-` / non-identifier handling is kept so the codec stays total and injective for any string (older regexes, `regExpToRoute` input): a prefix code, unlike a `-` → `_` sanitize. Output is `[A-Za-z0-9_]` (PCRE-legal).
- `fromGroupName()`: the single inverse (also strips the unnamed prefix), used by `getMatchParams`, the compiler's `scanRegExpGroups`, `regExpToRoute`. The compiler's runtime `_normalizeGroups` fallback inlines a copy; keep it in sync.
- Emission sites: `getParamRegexp()` and the four in `regexp.ts` (plain, mixed segment, modifier, `**:name`).
